= Compatibility Matrix

This page summarizes the versions of Java and Docx4J known to work with each Office‑stamper version, and lists notes about DOCX “producers” (the applications used to author templates: Word, Google Docs, LibreOffice, WPS…).

The goal is to help you quickly pick matching versions and be aware of common editor quirks.
If something is unclear for your setup, please open an issue, and we will extend this page.

== How to read this matrix

* Java shows the minimum compiler/bytecode level required by that Office‑stamper line.
Newer JDKs in the same major line usually work, but when the bytecode target is bumped, older JDKs will no longer run it.
* Docx4J column lists the exact versions we test against; adjacent patch releases in the same stream usually work as well.
* “Notes” provide important changes, (for example, a Java target bump) and links to additional tips.

== The two-module split (3.4.x)

Starting with 3.4.x, Office‑stamper is split in two Maven artifacts:

* `pro.verron.officestamper:engine` — the stamping engine itself. It has *no* docx4j dependency at all:
  it owns the SpEL machinery, the processor pipeline, the resolvers and the
  `pro.verron.officestamper.spi` contracts. It runs on any OOXML object model you can adapt.
* `pro.verron.officestamper:officestamper-docx4j11` — the docx4j 11.x provider
  (tested against 11.5.14).
* `pro.verron.officestamper:officestamper-docx4j17` — the docx4j 17.x provider
  (tested against 17.0.2). In docx4j 17 every JAXB object model (wml, dml, pml, sml)
  ships in the single `docx4j-generated-objects` artifact and the parent-tracking
  `Child` interface moved to `org.jvnet.jaxb.lang`; both providers are drop-in
  equivalents at the OfficeStamper level — swap the artifact to change the docx4j line.

Each provider is the ONLY place that knows about `org.docx4j`; it adapts docx4j objects
to the spi and registers the docx processors, resolvers and preprocessors you know from
previous releases (`DocxOfficeStampers.standard()` replaces the old `OfficeStampers` presets).

Most users should depend on one provider, which pulls the engine transitively.
The engine alone is useful only if you plan to write your own provider for another OOXML library.
Caveat: the `toAsciidoc`-style rendering machinery in `pro.verron.asciidoc:asciidoc-docx`
is still pinned to docx4j 11 module names, so until that library ships a docx4j17-flavoured
build, prefer `officestamper-docx4j11` if you also use the asciidoc converters.

== Migrating from 3.3.x

In 3.3.x you depended on `pro.verron.office-stamper:engine` and added docx4j yourself;
the engine contained everything, and `pro.verron.officestamper.preset.OfficeStampers`
was the entry point. The 3.4 migration is:

. *Dependency*: replace `pro.verron.office-stamper:engine` with
  `pro.verron.officestamper:officestamper-docx4j11` (or `-docx4j17`).
  The manual `docx4j-core` / `docx4j-JAXB-ReferenceImpl` dependencies become unnecessary —
  the provider brings the right docx4j line itself.
  The `engine` artifact still exists (the provider depends on it), but depending on it alone
  fails at runtime with `No OfficeStamper provider found on the classpath` — that error is the
  signal that the provider artifact is missing.
. *Entry point*: `OfficeStampers.docxStamper()` becomes `DocxOfficeStampers.standard()`.
  The old `pro.verron.officestamper.preset.OfficeStampers` name still exists but is now the
  docx-free factory — its method signatures changed, so calls must move to the new name.
. *Compatibility shims* (deprecated, `forRemoval`) keep the pre-3.4 package locations compiling
  in the `officestamper-docx4j11` artifact:
  `pro.verron.officestamper.utils.{wml, openpackaging, image, pml, sml}.*`,
  `pro.verron.officestamper.experimental.ExperimentalStampers`, and the docx-coupled preset
  processors/visitors under their old `preset.preprocessors.*`, `preset.postprocessors.*`,
  `preset.processors.repeat.*` and `preset.resolvers.image.*` locations.
  Each shim extends the relocated implementation, so instances remain assignable.
. *Not shimmable* — these changed shape and need a real port:
  the old `pro.verron.officestamper.api.{Comment, Insert, Paragraph, ProcessorContext, …}`
  contracts became the docx-free `pro.verron.officestamper.spi` contracts (custom processors
  written against raw docx4j types must be rewritten against the spi);
  `core.StandardParagraph` / `StandardTable` / `Tag` and friends are engine internals that
  became provider adapters; and the docx-coupled factory classes that lived directly in
  `pro.verron.officestamper.preset` (`OfficeStampers`, `Preprocessors`, `Postprocessors`)
  cannot be re-created at their old location because the package is owned by the engine's
  docx-free preset — they moved to `docx4j11.preset`.

== Experimental pptx / xlsx stampers

The provider artifact also carries the experimental `ExperimentalStampers`
(`pptxStamper()`, `xlsxPackageStamper()`), used by the command‑line interface for `.pptx` templates.

These stampers remain experimental:

* they run a minimal resolution pipeline (direct SpEL against the context) and do NOT go through
  the full processor pipeline — comment processors, resolvers and preprocessors do not apply;
* their APIs and behaviour may change without notice.

For production stamping, rely on the docx pipeline only.

== DOCX producers (template editors)

Different applications generate slightly different DOCX structures.
Office‑stamper aims to be robust across the major producers, but here are practical notes and links to tips:

=== Microsoft Word (Windows/Mac)

* Recommended for authoring templates; feature‑complete for comments, content controls, fields, smart tags and images.
* Templates created with recent Microsoft 365, 2021 and 2019 versions are known to work well.

=== Google Docs

* Supported for common scenarios.
Google Docs can serialize comments, and some fields differently from Word.
* If a comment‑based processor doesn’t trigger or tags appear missing, simplify formatting or recreate comments in Word.
* See link:troubleshooting.html[Troubleshooting] for diagnostic tips.

=== LibreOffice

* Supported; prefer simple formatting when placing expressions and comment processors.
* In some cases, advanced content controls/smart‑tags authored elsewhere may be flattened or altered.
* If placeholders aren't detected, try recreating the selection or comments, or switch to Word for template authoring.

=== WPS Office

* Supported with caveats similar to LibreOffice.
Some versions produce non‑standard anchors for comments.
* Validate templates with a minimal reproduction if you rely heavily on nested comments or complex formatting.
